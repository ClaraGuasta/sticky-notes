# Sticky Notes

A single-page sticky notes board built with **React + TypeScript**, without UI or drag-and-drop libraries. Styling uses Tailwind CSS (utility classes only, no component kit).

## Features

**Required**
- **Create** a note at a chosen position and size: click **+ New note**, then click on the board (default size) or drag to draw the note's exact rectangle. `Esc` cancels.
- **Move** a note by dragging its top bar.
- **Resize** a note by dragging its bottom-right corner (minimum 120x120).
- **Delete** a note by dropping it on the trash zone (bottom-right). The trash highlights while a note hovers over it.

**Bonus**
- Edit note text (new notes are focused automatically, so you can type right away).
- Bring notes to front: clicking anywhere on a note raises it above the others.
- Different colors: new notes get a random color, which can be changed from the note's top bar (on hover or keyboard focus).
- Persistence to `localStorage`, restored on page load.
- Persistence to a mocked async REST API, with simulated latency and optional failures.

**Extras**
- First-run onboarding: an empty-board hint pointing to the create button, and a one-time tip next to the first note explaining the gestures.
- Notes are kept inside the board when dropped, so they can't get lost off-screen.
- Loading and error states while the notes are fetched.

## Getting started

Requires **Node.js 20.19+ or 22.12+**.

```bash
npm install
npm run dev        # http://localhost:5173
```

Other scripts:

```bash
npm run build      # type-check (tsc -b) and production build into dist/
npm run preview    # serve the production build
npm run lint       # ESLint
npm test           # unit tests (Vitest, watch mode); use `npx vitest run` for a single run
```

### Choosing the storage backend

Copy `.env.example` to `.env` and set:

```bash
VITE_USE_MOCK_API=true    # async mock REST API (default)
VITE_USE_MOCK_API=false   # plain localStorage
```

If no `.env` is present, the mock API is used.

## Architecture

All note data lives in a single `useReducer` store (`domain/notesReducer.ts`). Actions are a discriminated union that describes domain events (`note/moved`, `note/resized`, `note/broughtToFront`, …) rather than generic updates, so business rules live in one place: the reducer assigns z-indexes, enforces the minimum size and skips no-op updates by returning the same state reference. The reducer stays pure; impure values such as ids (`crypto.randomUUID`) and random colors are generated by the caller before dispatching. Components are thin: `Board` and `NoteCard` receive data and callbacks, and `App` acts as the composition root that wires state, persistence and handlers together. Domain types and logic (`domain/`) know nothing about React or styling.

Every gesture (move, resize, create) is built on one generic hook, `usePointerDrag`, which uses Pointer Events with pointer capture so a drag keeps tracking even when the cursor leaves the element or the window. Performance was a primary concern: while dragging, the in-progress offset is local state of the dragged card, and the store receives a single action when the gesture ends instead of one per mouse move. Notes are rendered with `React.memo` and stable callbacks, and the reducer preserves the identity of untouched notes, so moving or editing one note re-renders only that note. Positioning uses `transform: translate()` instead of `top`/`left` to avoid layout recalculation. The trash works by hit-testing the pointer against the trash rectangle; the note only reports where it was dropped, and the board decides whether that is a move or a delete, so the note component has no knowledge of drop targets. The notes layer is an isolated stacking context, so ever-growing z-indexes never cover the board UI.

Persistence sits behind a `NotesRepository` interface (`load`/`save`, both async) with two implementations: `localStorage` and a mock REST API that simulates `GET`/`PUT /api/notes` with random latency (it uses `localStorage` under a separate key as its fake server database). The app depends only on the interface; the concrete implementation is chosen in one place. The `useNotesPersistence` hook loads the notes on mount, does not save until the initial load has finished (otherwise the empty initial state would overwrite stored data), debounces saves by 300 ms and runs them sequentially, so a slow, older request can never overwrite a newer one. Anything read from storage or the network is treated as `unknown` and validated with type guards (`parseNotes`); malformed notes are dropped individually instead of failing the whole load.

## Project structure

```
src/
  domain/         Note model, reducer and geometry helpers (pure, framework-agnostic)
  hooks/          usePointerDrag, useNotesPersistence, useOnboardingFlag
  persistence/    NotesRepository interface, localStorage and mock API implementations, validation
  components/     Board, NoteCard, TrashZone, ColorPicker, EmptyState, FirstNoteTip, StatusMessage
  styles/         Shared Tailwind class maps for note colors
```

Unit tests live in `__tests__` folders next to the code they cover. They focus on the pure logic (reducer, geometry and parsing) and follow the Arrange-Act-Assert pattern.

## Assumptions and decisions

- **Desktop only**, as stated in the requirements (minimum resolution 1024×768). Touch devices were not targeted.
- **The board is the viewport.** There is no scrolling or zooming canvas.
- **Creation is an explicit mode.** A plain click on the board does nothing, to avoid creating notes by accident (for example, when clicking away from a note being edited). The mode makes "specified position and size" explicit: click for a default-size note, or drag to draw it.
- **Notes are clamped inside the board on drop.** During the drag they can cross the edge and snap back on release, which keeps the interaction code simple.
- **The mock API saves the whole collection** (`PUT /api/notes`) rather than exposing per-note endpoints, which matches the size of the data.
- **Onboarding state is a UI preference**, stored directly in `localStorage`, independently of the notes backend.

## Known limitations and possible improvements

- If the window is shrunk after notes were placed, some notes may end up partially outside the board until moved.
- Save errors are logged to the console but not shown in the UI. A small "saving / saved / failed" indicator with retry would be the next step.
- Moving and resizing are pointer-only. Keyboard support (for example, arrow keys on a focused note) would improve accessibility.
- No undo for deletions.
- No synchronization between multiple open tabs.
- Component and interaction tests (React Testing Library or Playwright) would complement the current unit tests.
